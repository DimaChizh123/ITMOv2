# Размышления об использовании SDD

## Контекст

Я попробовал реализовать дополнительные фичи для моего MCP по судоку. Для начала я сделал простую фичу справочника паттернов с использованием OpenSpec.

## OpenSpec: строгость процесса

OpenSpec требует строгой последовательности шагов:

1. explore
2. propose
3. apply
4. sync
5. archive

и использования специальных команд. Это позволяет удобно реализовать одну фичу в рамках одного разработчика.

## Spec Kit: «конституция» и шаблоны

Spec Kit предоставляет «конституцию», которая неизменяема и применима для всех аспектов разработки в проекте. Также в Spec Kit идёт упор на шаблоны markdown‑файлов, а не на команды, что позволяет удобно вести разработку в параллельных командах, а потом сливать всё в общий контракт.

## Согласование UI и логики

До согласования спеки UI и логики сильно различались. Спека UI была более удобна для реализации HTML‑страницы, а спека логики — удобнее для переноса на код. В процессе согласования зафиксировали единые правила:

- Индексация: в логике строки и столбцы были 0‑based, а в UI — 1‑based. В итоге зафиксировали 0‑based, но с отображением 1‑based.
- Обработка ошибок: до согласования при обнаружении ошибки сетки HTML‑страница не возвращалась; после согласования страница отображает ошибку.
- Формат данных: раньше UI содержал свой формат JSON; после согласования он берёт JSON от logic.
- Прочие поля JSON: были дополнительные расхождения, но почти всё зафиксировано в contract.

## Итог

SDD — довольно удобный инструмент, и разные фреймворки удовлетворяют разным задачам. Он позволяет фиксировать изменения и пожелания для фич в удобном формате как для человека, так и для ИИ‑агента.
