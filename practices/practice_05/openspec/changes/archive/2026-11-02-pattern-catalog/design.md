# Design

## Источник данных
- Реестр карточек — статический словарь в `mcp/sudoku/index.py`, ключ — `id` (напр. `x_wing`), значение — описанная карточка (см. схему в spec).
- Реестр синхронизируется с `sudoku.hint`: каждый `result.type` (кроме `none`) обязан иметь карточку с совпадающим `id`.

## Обработка запроса
- Ветка `tool == "sudoku.patterns"`:
  - Если `args` пуст или `{}` → вернуть список `patterns` (ключи реестра).
  - Если `args.pattern` строка → вернуть карточку; неизвестный `id` → `{"ok": false, "error": "Unknown pattern id: <id>"}`.
  - Любые иные/лишние аргументы → строгая ошибка: `{"ok": false, "error": "Invalid arguments: only 'pattern' is supported"}`.
  - Поле `grid` не допускается в этом tool.
- Сериализация JSON — `ensure_ascii=False`.
- Сообщение об неизвестном tool обобщено:
  - `{"ok": false, "error": "Unknown tool. Use sudoku.hint or sudoku.patterns"}`.

## Схема карточек
- Обязательные поля: `id`, `title`, `difficulty`, `summary`, `intuition`, `how_to_apply`, `example.grid`, `example.highlights`.
- Опциональные: `common_mistakes`, `see_also`.
- Индексация координат — 0-based.
- Пример должен быть «живым» (реалистическая 9×9 сетка), а не матрица из нулей; `highlights` содержат ключевые клетки и удаления.

## Политика расширения
- Добавление нового `type` в `sudoku.hint` требует:
  1) карточку с таким же `id` в реестре,
  2) обновление verify-сценариев: список должен включать новый `id`, базовая проверка карточки.
- Изменение сообщения об неизвестном tool сопровождается корректировкой verify.

## Совместимость
- Поведение `sudoku.hint` не меняется.
- `sudoku.patterns` не принимает `grid`.

## Agent Policy and UX
- Политика объяснений:
  - При запросе теории/объяснения техники вызывать MCP `sudoku.patterns` с `args.pattern`, равным `result.type` из ответа `sudoku.hint`.
  - Если `sudoku.patterns` недоступен, кратко объяснять простыми словами и указывать идентификатор техники; не пытаться решать судоку самостоятельно.
- Стандартизация ответа агента:
  - По умолчанию verbose включён; выключать только по явной просьбе или при необходимости минимального вывода.
  - Формат ответа:
    1) тип техники (`result.type`),
    2) краткое человеческое пояснение (summary/intuition),
    3) шаги применения (3–5),
    4) затем структурированные данные из MCP.
- Ошибки входа:
  - При не 9×9/не 0–9/противоречиях — возвращать сообщение MCP без попыток «починки»; просить пользователя предоставить валидную сетку.
- Операционный флоу:
  - Валидация входа → вызов `sudoku.hint` → представление результата → по запросу — `sudoku.patterns` по `result.type`.
- Примечание про verify-логи:
  - Исторически сообщения могли упоминать “index.js/node”; ориентироваться на смысл, а не формулировку.
